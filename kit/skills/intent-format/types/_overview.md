# Card types — overview

> Generated by `intent-format build-kit` from `schema.json` — do not edit by hand.

The modelling cheat sheet: pick the type by its purpose, then check what it is not. Details per type: `types/<type>.md`.

**project** · PR · `project.md` — The front door: what the product is and for whom, main use cases, constraints, vocabularies and project-wide tech.
- not manifest: intent-format.md describes the KB as an artifact (version, lifecycle, modules); project.md describes the product.
- not feature: A top-level Feature scopes one product domain; the project card frames the whole product.

**role** · RO · `roles/` — A user type: who uses the product, why they come and how they use it. User stories name it.
- not state: A State is a mode in which a different set of screens exists (signed in vs signed out); a role is who is there. A role lists the States it can be in with state:.
- not feature: What a role wants is its user stories, written on features and the project card; the role card lists them in ⚙ Stories, never restates them.

**screen** · SC · `screens/` — A place the user can be: what it is for and what it is made of.
- not component: Hosts its own component list → screen (modal/panel via opens-as); a piece placed inside places (row, toast, menu) → component; the frame around places → shell.
- not screen-variant: Same place with another composition or presentation → a variant; a different purpose → a new screen.
- not ia: A screen never states where it sits or what it leads to; IA maps arrange screens.

**component** · CP · `components/` — A reusable part placed in screens or other components: what it does wherever it appears.
- not shell: The frame around places, described once and resolved per placement → shell. A part inside places → component.
- not screen: Navigated to, or hosts its own component list → screen.
- not tech: The library or service it is made with is tech; the UI part is the component.

**shell** · SH · `shells/` — The frame around places: what is always there, where it leads, and the rules for whatever it frames. Described once, resolved per placement.
- not screen: A place the user goes to, with content of its own → screen. The frame that unfolds around it (navigation drawer, account menu) → a part of the shell.
- not component: A shell is never placed as a Part; it frames. Its own parts (top bar, burger, breadcrumbs) are components.
- not ia: A shell says what surrounds a place; the map says where the place sits. A node binds a shell with · shell:.

**userflow** · UF · `userflows/` — A journey in one file: typed steps, an ordered step list per variant, and fork wiring.
- not feature: A Sub-feature is a capability; the flows homed in it say how the user moves.
- not edge-case: A named exceptional situation with agreed handling is an edge case whose Where points at the step.
- not rule: Policy behind a fork branch is cited with · rule: #RL…, never paraphrased.

**ia** · IA · `ia/` — One IA map: screens arranged in a hierarchy plus lateral edges — pure arrangement.
- not screen: A map holds only references; screen facts live on the screen.
- not userflow: A map says where places sit; a flow says how a user moves through them.

**rule** · RL · `rules/` — One business rule stated once, in plain words; every other card references it.
- not edge-case: A situation plus its agreed handling is an edge case; the policy it applies is a rule.
- not flow-step: A fork is a decision point in a journey; it cites the rule.
- not requirement: An acceptance criterion of one card stays in that card's Description.

**api** · AP · `apis/` — One API call: method, endpoint, what it does and the backend node that serves it.
- not backend: The node that serves calls is backend; the call is api.

**feature** · FT · `features/` — A product domain (Feature) or a capability inside one (Sub-feature, with parent:).
- not userflow: A Sub-feature names a capability; the flows homed in it describe how the user moves.
- not project: The project card frames the whole product; a Feature scopes one domain.
- not rule: Numbers, limits and conditions go to rules, never into a Feature's description.
- not ia: Where a feature is reached from is navigation (the IA map, a screen's Navigation); the feature tree groups by purpose, never by screen.

**edge-case** · EC · `edge-cases/` — A named exceptional situation: what happens (If/Then) and every place it can occur.
- not rule: The policy applied is a rule; the situation and its handling is the edge case.
- not requirement: Normal-path acceptance criteria stay in the owning card.
- not userflow: An edge case that grew steps becomes a small flow attached where it applies.

**backend** · BN · `backend/` — A backend node of this product and its connections.
- not tech: The technology a node runs on is tech (Built with); the node itself is backend.
- not api: Each call is an api card that names this node in Served by.

**tech** · TC · `tech/` — A technology the product uses or considers: what it is, why, and the alternatives.
- not backend: A node of this product is backend; what it runs on is tech.
- not component: An integration component wraps a provider inside the UI; the provider technology is tech.

**decision** · DC · `decisions/` — A question that needs or got a decision: options, outcome and the cards it affects.
- not comment: A remark on a card is a comment; a choice between options that changes cards is a decision.
- not flow-step: A fork is a runtime branch in a journey, not a product decision.

**comment** · CM · `comments/` — One remark, attached from the cards it is about; its text lives only here.
- not decision: If it needs a choice between options, open a decision.

Sub-documents have their own core but no file: screen-variant (SV, a `### ` sub-document in ## Variants of a screen) · component-variant (CV, a `### ` sub-document in ## Variants of a component) · shell-variant (HV, a `### ` sub-document in ## Variants of a shell) · flow-step (FS, a `### ` sub-document in ## Steps of a userflow).

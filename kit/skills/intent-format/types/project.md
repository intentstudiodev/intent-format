# project · PR · `project.md`

> Generated by `intent-format build-kit` from `schema.json` — do not edit by hand.

The front door: what the product is and for whom, main use cases, constraints, vocabularies and project-wide tech.

**When to use.** Exactly one per workspace, at its root; the first card an agent reads.

**Not to confuse with**
- **manifest** — intent-format.md describes the KB as an artifact (version, lifecycle, modules); project.md describes the product.
- **feature** — A top-level Feature scopes one product domain; the project card frames the whole product.

## Front matter

| Key | Required | Values |
|---|---|---|
| `standard` | yes | `IntentFormat/1.2` — always the first key |
| `type` | yes | `project` |
| `id` | yes | `PR000000`-style core (PR + 6 digits) — minted by `intent-format new`, never by hand |
| `name` | yes | the card name (no `[` `]`); title, references and filename slug derive from it |
| `status` | yes | status vocabulary below, or `—` |
| `industry` | no | The product's domain, free text (E-commerce, Travel, Fintech, Health, Education, Media, SaaS tool, Logistics, Hospitality, Real estate, Social, Gaming …). Agents read it first: it sets the vocabulary, the usual journeys and the rules that apply. |
| `audience` | no | Who the product is sold or given to: B2C, B2B, B2B2C, Internal system, Marketplace — one or several. With industry it frames every suggestion an agent makes. |
| `origin` | no | `<kb>/<core>` — written by import |
| `x-*` | no | extension keys; kept untouched, always last |

Keys in this order. Unknown = `—` (never quoted); `version`-like values are quoted.

## Status

`Idea` · `In design` · `Approved` · `In build` · `Live` · `Parked` — Product lifecycle; Parked = set aside from any stage. Movement is free in both directions. Template: `—`. status: — when there is no evidence for any value. Status only with evidence.

## Sections

| Section | Kind | Guidance |
|---|---|---|
| ## Description | required | What the product is and for whom, in a few sentences; product-wide requirement blocks if any. |
| ## Why | required | What problem does the product solve, for whom, and why now? Text (optionally ending [likely] or [assumed]), none[ — note], same as #<id> (another card's why covers it) or —. |
| ## User stories | required | 5–10 lines: - As a <Role>, I want <goal>, so that <benefit>. <Role> is the exact name of a role card (roles/). |
| ## Keep in mind | required | Non-functional requirements (performance, offline, privacy, accessibility, languages) as requirement blocks; none if there are none. |
| ## Vocabularies | required | The only place States, Platforms, Opens-as values and Tech categories are defined; all start empty. User types are role cards (roles/); a ### Roles table is deprecated (W050, intent-format migrate). |
| ## Built with | required (optional without tech/) | Project-wide technologies: TC references; an open need is [~ <generic name>] plus an Open decision. Default relation: Built with. |
| ## Links | optional | External links: - [title](url) · type: Design\|Code\|Doc\|Source\|Analytics\|Other. Source = evidence (inputs/ file or URL). Default relation: Link. |
| ## Tags | optional | One line of comma-separated tags. |
| ## Comments | optional | Comment cards attached here, one line each; the remark lives in the CM file. Default relation: Comment. |
| ## ⚙ Decisions | generated | Decisions that affect this card. |

Body states: `—` alone = unknown (counted) · `none` alone = verified empty · a final `- —` / `N. —` list item = more items exist but are unknown. Never edit `⚙` sections or the `> ⚙` status line — run `intent-format regen`.

**Why.** `## Why` is required here. Its question (purpose): *What problem does the product solve, for whom, and why now?* It holds one of: the answer in one or two sentences, optionally ending `[likely]` (follows from inputs) or `[assumed]` (a guess; counted as open) — unmarked means confirmed; `none` or `none — <note>` (no why needed; not counted); `same as #<id>` (another card's why covers it; check follows the link); or `—` (nobody asked yet; counted as why debt). A Why says what the Description does not; a question for the owner goes in the sentence it concerns as `[ask: …]`.

## Requirement blocks

Requirement blocks sit in Description (and the project's Keep in mind, and step bodies), after the descriptive prose. Marker `**R<n> · <Preset>**`: n is unique within the file; never reused or renumbered. Default preset here: **Checklist** (any preset is legal anywhere; the default is the one templates and agents use first.)

```markdown
**R1 · User story** As a <role>, I want <goal>, so that <benefit>.

**R2 · GWT**
Given <context>
When <event>
Then <observable outcome>

**R3 · EARS** [When <trigger>|While <state>|If <condition>|Where <feature>, [then ]]the system shall <response>.

**R4 · Checklist**
- [ ] <verifiable item>
```

**User story**: so that is mandatory; <role> is the exact name of a role card. · **GWT**: All three keywords present, in this sequence. · **EARS**: Contains "the system shall". · **Checklist**: At least one item. A slot written as — is a declared blind spot (counted).

# Example app · #PR000001
> ⚙ #PR000001V1.0 · V1.0 in-progress

## Description
A small app in which a Member keeps a list of items: create, browse and change them.


## Why
Members lose track of things kept in notes and chats; one list that is always at hand fixes that.
## User stories
- As a Member, I want to create an item, so that I can keep track of it.
- As a Member, I want to browse my items, so that I find one quickly.
- As a Member, I want to edit an item, so that its details stay current.
- As a Member, I want to change my settings, so that the app fits how I work.
- As an Admin, I want to review all items, so that the list stays clean.

## Keep in mind
**R1 · Checklist**
- [ ] The Item list opens in under one second with 1000 items.
- [ ] Every screen works with the keyboard alone.

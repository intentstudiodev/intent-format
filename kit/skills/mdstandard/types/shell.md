# shell · SH · folder `shells/`

> Generated by `mds build-kit` from `schema.json` — do not edit by hand.

The frame around places: what is always there, where it leads, and the rules for whatever it frames. Described once, resolved per placement.

**When to use.** Persistent UI around places: the app frame (navigation, account, consent), a section's back and breadcrumbs, a stepper's progress and Continue, a modal's title, close and confirm, a focus mode, a split view, an embedded host. Typically three to eight per product.

**Not to confuse with**
- **screen** — A place the user goes to, with content of its own → screen. The frame that unfolds around it (navigation drawer, account menu) → a part of the shell.
- **component** — A shell is never placed as a Part; it frames. Its own parts (top bar, burger, breadcrumbs) are components.
- **ia** — A shell says what surrounds a place; the map says where the place sits. A node binds a shell with · shell:.

**How to model**
- Screens are content, shells are context. A screen says what the place is for, its outcome and its primary action by name; the shell says what surrounds it and renders that action.
- Does the user go somewhere with a purpose of its own → a screen (a modal or sheet via appears-as). Does the frame unfold (a navigation drawer, an account menu) → a part of the shell with · appears-as:.
- New shell or variant? A new shell when the frame does another job (another shell-type) or follows another navigation model — mostly different destinations or parts, or different rules in ## Places inside (a variant cannot change them). A variant when the same frame adds or swaps a part or two for a platform, a state or a level.
- Typical set: one app shell per platform family whose frame is built differently (a desktop header vs a native tab bar), a section shell per area with its own wayfinding, a stepper per task flow, one overlay shell per presentation.
- Variants stack: every variant whose passport matches applies, so write Signed in, Level 2+ and Mobile once each — never their combinations.
- Navigation is one ordered list on the host, in display order. A line shown only on some platforms or in some states carries · platform: / · state:; · in: names the part that holds the entry (Header, Footer, Tab bar, Account menu).
- Write the exception, not the rule: every page gets the app shell of its platform and state, every modal the Modal shell. Bind a section once on its map node (· shell:). Run mds frame <root> <screen> to see what a place resolves to.

**Altitude.** What the frame provides and demands — never the content of the places inside it.

## Requirement blocks

Requirement blocks sit in Description & Requirements (and the project's Constraints, and step bodies), after the descriptive prose. Marker `**R<n> · <Preset>**`: n is unique within the file; never reused or renumbered.

```markdown
**R1 · User story** As a <role>, I want <goal>, so that <benefit>.

**R2 · GWT**
Given <context>
When <event>
Then <observable outcome>

**R3 · EARS** [When <trigger>|While <state>|If <condition>|Where <feature>, [then ]]the system shall <response>.

**R4 · Checklist**
- [ ] <verifiable item>
```

**User story**: so that is mandatory; <role> is the exact name of a role card. · **GWT**: All three keywords present, in this sequence. · **EARS**: Contains "the system shall". · **Checklist**: At least one item. A slot written as — is a declared blind spot (counted).

## Sub-document: shell-variant

Heading `### <Name> · #HV<6 digits>` in ## Variants; anchor `<a id="hv000001"></a>` on the next line.
Optional passport line: `platform:` · `state:` · `level:` (as listed; omit keys at their default).
Optional one prose line, then the parts this variant ADDS to the host's ## Components, as ordered Part lines (or none / —); explicit - Comment: and - Link: lines may follow.
- A shell variant adds parts to the host's ## Components; it never repeats them (the one place the all-parts rule of screen and component variants is relaxed).
- Variants stack: every variant whose passport matches the placement's platform, state and level applies, in variant order; none matching = the host alone. Never write a variant for a combination.
- Navigation lines live only in the host's ## Navigation; limit them with · platform: / · state:.
- Variant names are unique within the host.

# role · RO · folder `roles/`

> Generated by `mds build-kit` from `schema.json` — do not edit by hand.

A user type: who uses the product, why they come and how they use it. User stories name it.

**When to use.** One card per kind of user the product serves (Guest, Member, Admin), and per kind of user of a neighbouring system the product must know about (back-office staff). Not a persona: a named person with a story is future work.

**Not to confuse with**
- **state** — A State is a mode in which a different set of screens exists (signed in vs signed out); a role is who is there. A role lists the States it can be in with state:.
- **feature** — What a role wants is its user stories, written on features and the project card; the role card lists them in ⚙ Stories, never restates them.

**Altitude.** Who they are and why they come — never the steps they take (flows) or the policy that limits them (rules).

## Front matter

| Key | Required | Values |
|---|---|---|
| `standard` | yes | `MDStandard/1.0` — always the first key |
| `type` | yes | `role` |
| `id` | yes | `RO000000`-style core (RO + 6 digits) — minted by `mds new`, never by hand |
| `name` | yes | the card name (no `[` `]`); title, references and filename slug derive from it |
| `status` | yes | status vocabulary below, or `—` |
| `state` | no | a State of project.md (one value or a list); omitted = Shared; only when States are declared |
| `platform` | no | a value of ### Platforms in project.md (or `All`) — Platforms this role uses; omitted = all. Their frames are the app shells of these platforms. |
| `origin` | no | `<kb>/<core>` — written by import |
| `x-*` | no | extension keys; kept untouched, always last |

Keys in this order. Unknown = `—` (never quoted); `version`-like values are quoted.

## Status

`Idea` · `In design` · `Approved` · `In build` · `Live` · `Parked` — Product lifecycle; Parked = set aside from any stage. Movement is free in both directions. Template: `—`. status: — when there is no evidence for any value. Status only with evidence.

## Sections

| Section | Kind | Guidance |
|---|---|---|
| ## Description & Requirements | required | Who they are, their context, what they come to do and what matters to them (devices, frequency, expertise, accessibility needs); requirement blocks only for needs that hold wherever this role appears. |
| ## Links | optional | External links: - [title](url) · type: Design\|Code\|Doc\|Source\|Analytics\|Other. Source = evidence (inputs/ file or URL). Default relation: Link. |
| ## Tags | optional | One line of comma-separated tags. |
| ## Comments | optional | Comment cards attached here, one line each; the remark lives in the CM file. Default relation: Comment. |
| ## ⚙ Stories | generated | Every user story that names this role: Main use cases and User story blocks on any card. |
| ## ⚙ Decisions | generated | Decisions that affect this card. |

Body states: `—` alone = unknown (counted) · `none` alone = verified empty · a final `- —` / `N. —` list item = more items exist but are unknown. Never edit `⚙` sections or the `> ⚙` status line — run `mds regen`.

## Requirement blocks

Requirement blocks sit in Description & Requirements (and the project's Constraints, and step bodies), after the descriptive prose. Marker `**R<n> · <Preset>**`: n is unique within the file; never reused or renumbered.

```markdown
**R1 · User story** As a <role>, I want <goal>, so that <benefit>.

**R2 · GWT**
Given <context>
When <event>
Then <observable outcome>

**R3 · EARS** [When <trigger>|While <state>|If <condition>|Where <feature>, [then ]]the system shall <response>.

**R4 · Checklist**
- [ ] <verifiable item>
```

**User story**: so that is mandatory; <role> is the exact name of a role card. · **GWT**: All three keywords present, in this sequence. · **EARS**: Contains "the system shall". · **Checklist**: At least one item. A slot written as — is a declared blind spot (counted).

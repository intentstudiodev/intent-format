# feature · FT · folder `features/`

> Generated by `mds build-kit` from `schema.json` — do not edit by hand.

A product domain (Feature) or a capability inside one (Sub-feature, with parent:).

**When to use.** Feature: one per product domain. Sub-feature: one per user-facing capability named by its outcome, under its Feature. Screens, flows and components point at their home with feature:.

**Not to confuse with**
- **userflow** — A Sub-feature names a capability; the flows homed in it describe how the user moves.
- **project** — The project card frames the whole product; a Feature scopes one domain.
- **rule** — Numbers, limits and conditions go to rules, never into a Feature's description.

**Levels.** Feature: Top-level product domain; no parent:. Sub-feature: A capability; parent: <FT core of a Feature>. Max two levels.

**Altitude.** Feature: Why it exists and its scope in/out. Sub-feature: What capability, for whom.

## Front matter

| Key | Required | Values |
|---|---|---|
| `standard` | yes | `MDStandard/1.0` — always the first key |
| `type` | yes | `feature` |
| `id` | yes | `FT000000`-style core (FT + 6 digits) — minted by `mds new`, never by hand |
| `name` | yes | the card name (no `[` `]`); title, references and filename slug derive from it |
| `status` | yes | status vocabulary below, or `—` |
| `state` | no | a State of project.md (one value or a list); omitted = Shared; only when States are declared |
| `parent` | no | pattern `^FT\d{6}$` — Sub-features only: FT core of their top-level Feature. |
| `priority` | no | `High` · `Medium` · `Low` — Delivery priority. |
| `origin` | no | `<kb>/<core>` — written by import |
| `x-*` | no | extension keys; kept untouched, always last |

Keys in this order. Unknown = `—` (never quoted); `version`-like values are quoted.

## Status

`Idea` · `In design` · `Approved` · `In build` · `Live` · `Parked` — Product lifecycle; Parked = set aside from any stage. Movement is free in both directions. Template: `—`. status: — when there is no evidence for any value. Status only with evidence.

## Requirement blocks

Requirement blocks sit in Description & Requirements (and the project's Constraints, and step bodies), after the descriptive prose. Marker `**R<n> · <Preset>**`: n is unique within the file; never reused or renumbered. Default preset here: **User story** (any preset is legal anywhere; the default is the one templates and agents use first.)

```markdown
**R1 · User story** As a <role>, I want <goal>, so that <benefit>.

**R2 · GWT**
Given <context>
When <event>
Then <observable outcome>

**R3 · EARS** [When <trigger>|While <state>|If <condition>|Where <feature>, [then ]]the system shall <response>.

**R4 · Checklist**
- [ ] <verifiable item>
```

**User story**: so that is mandatory; <role> is the exact name of a role card. · **GWT**: All three keywords present, in this sequence. · **EARS**: Contains "the system shall". · **Checklist**: At least one item. A slot written as — is a declared blind spot (counted).

# Items · #FT000001
> ⚙ #FT000001V1.0 · V1.0 in-progress

## Description & Requirements
Members need one dependable place for the things they keep track of.

In scope: finding, creating and changing items. Out of scope: sharing items with other people.
